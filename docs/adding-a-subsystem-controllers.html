Make the mechanism follow the goal

Your buttons now change the target on the graph. Next, we’ll send that target to the Talon FX motor controller, the device that drives the motor. We use CTRE’s Phoenix library to configure it and send requests.

Add a Motion Magic request

Motion Magic moves toward a position using a planned speed and acceleration. The Talon compares the measured position with that plan and adjusts the motor output.

In your subsystem file, find the existing Phoenix imports:

TunerConstants.kCANBus selects the bus already set up by this project. positionRequest stores a reusable Motion Magic request, initially set to zero turns. Creating it does not send it to the motor.

public Elevator() {
    var config = new TalonFXConfiguration();
    config.Feedback.SensorToMechanismRatio = ElevatorConstants.GEAR_RATIO;
    config.Slot0.kP = 5.0;
    config.Slot0.kV = 2.4;
    config.Slot0.kG = 0.28;
    config.Slot0.GravityType = GravityTypeValue.Elevator_Static;
    config.MotionMagic.MotionMagicCruiseVelocity = 2.0;
    config.MotionMagic.MotionMagicAcceleration = 6.0;

    var status = motor.getConfigurator().apply(config);
    if (!status.isOK()) {
        throw new IllegalStateException("Elevator Talon FX configuration failed: " + status);
    }

    // Setup Simulation
    // Sets the simulated motor model. This setup is prepared for you; leave it in place.
    motor.getSimState().setMotorType(TalonFXSimState.MotorType.KrakenX60);
}

After — green lines are new or changed

public Arm() {
    var config = new TalonFXConfiguration();
    config.Feedback.SensorToMechanismRatio = ArmConstants.GEAR_RATIO;
    config.Slot0.kP = 45.0;
    config.Slot0.kV = 15.0;
    config.Slot0.kG = 0.23;

    config.MotionMagic.MotionMagicCruiseVelocity = 0.45;

        throw new IllegalStateException("Arm Talon FX configuration failed: " + status);

    motor.getSimState().setMotorType(TalonFXSimState.MotorType.KrakenX60);
}
  • new TalonFXConfiguration() starts a configuration object. The following assignments fill in its settings.
  • SensorToMechanismRatio tells Phoenix how many motor turns make one drum turn. This is the GEAR_RATIO constant we introduced in Mechanisms, now used to relate the motor’s rotation to the mechanism’s rotation.
  • Slot0 is the set of control gains used by this request. kP adds voltage based on position error, kV adds voltage for the planned velocity, and kG adds voltage to counter gravity.
  • GravityType selects constant gravity compensation for the elevator.
  • The Motion Magic settings limit the planned speed (mechanism turns per second) and acceleration (turns per second squared). These values and gains are prepared for our desktop model.
  • apply(config) sends the settings to the Talon. If it fails, the if block stops startup with an error describing the problem.
  • The last line tells Phoenix’s simulator which motor model we are using.

Send the saved goal to Phoenix

Here is where the two constants do different jobs. We already gave GEAR_RATIO to Phoenix as SensorToMechanismRatio, so its positions are now in drum turns. Our subsystem still accepts goals in meters. Use METERS_PER_DRUM_TURN to convert that height into drum turns before sending the request.

Find the private goal function you added in Buttons and Commands:

Before — find this code

}

Before — find this code

private void setAngleGoal(double goal) {

}

Keep the line that clamps and saves the goal. Add the two green lines to convert it into mechanism turns and send the position request:

After — green lines are new or changed

private void setHeightGoal(double goal) {
    targetMeters = Math.clamp(goal, ElevatorConstants.MIN_METERS, ElevatorConstants.MAX_METERS);
    double goalTurns = targetMeters / ElevatorConstants.METERS_PER_DRUM_TURN;
    motor.setControl(positionRequest.withPosition(goalTurns));
}

After — green lines are new or changed

private void setAngleGoal(double goal) {
    targetDegrees = Math.clamp(goal, ArmConstants.MIN_DEGREES, ArmConstants.MAX_DEGREES);
    double goalTurns = targetDegrees / 360.0;
    motor.setControl(positionRequest.withPosition(goalTurns));
}

Dividing meters by meters per drum turn converts our height into drum turns. A 0.65 m goal is about 4.14 drum turns. withPosition updates the request with that goal. motor.setControl sends it to the Talon, which continues running its position control after our one-shot command finishes.

Keep the target and actual logging you added earlier. The supplied simulationPeriodic() method updates the simulated mechanism and its motor sensor readings.

Checkpoint 2 · Compare target and actual

  1. Save and restart the simulator. Check port 1, reconnect AdvantageScope if needed, and keep target and actual on the same axis as before.
  2. Enable Teleop with the buttons released. Press the same high button, wait about three seconds, then press low. Disable when both moves are done.
  3. The target steps first, then actual position moves toward it. Check that the actual settles near the goal and that the Mechanism drawing follows it.

Done when the same buttons pass both checkpoints. Point out where the target and actual differ most and explain why.

The robot code fails to launch

Check that you opened the top-level Code2027-Preseason folder in WPILib 2027 VS Code. Read the first error in the terminal. A Java compile error will point to a file and line. A Talon configuration exception names the subsystem and reports the Phoenix status. Recheck the CAN ID and bus against the example for your mechanism.

The drawing appears but the numeric fields are missing

Check that you restarted the robot after editing and that the expected telemetry.log call is in the existing periodic() override. Check the spelling and capital letters in your mechanism’s name and the field names.

The target stays flat when I press high

Verify Teleop is enabled and your controller is assigned to port 1. Release the button, then press it again while watching the target line in AdvantageScope. Check that the high button calls your command in configureElevatorBindings(), that runOnce calls the private setter, and that periodic() logs the target field.

The target moves but actual stays flat or moves the wrong distance

Check that simulationPeriodic() calls sim.step(motor.getSimState()) and that SensorToMechanismRatio matches the gear ratio in Constants.java. Compare the request against the expected drum or arm turns. A correct drawing with a wrong graph scale points to the conversion in periodic().

AdvantageScope shows no data

Use desktop AdvantageScope 2027 on the same computer as the simulator. Select ordinary NetworkTables in the simulator connection menu. Look for Telemetry → Swerve first. If that table is absent too, check that the robot is running and close any second simulator instance.
