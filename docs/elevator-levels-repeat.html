Repeat presses

The elevator already exposes commands that own a complete movement. We will keep that interface and change how the buttons start those commands.

10. Import the command builders

Open src/main/java/first/robot/RobotContainer.java. Find this code:

Before — red marks the code being changed

import org.wpilib.command2.Command;

Open RobotContainer.java. Add Commands alongside the existing Command import. Commands provides small command builders, including runOnce.

After — green marks the added code

import org.wpilib.command2.Command;
import org.wpilib.command2.Commands;

11. Start a fresh movement on each press

Open src/main/java/first/robot/RobotContainer.java. Find this code:

Before — red marks the code being changed

        operator.a().onTrue(elevator.decreaseLevelCommand());
        operator.y().onTrue(elevator.increaseLevelCommand());

Replace the two bindings in configureElevatorBindings. The outer command runs once and finishes immediately. Its arrow expression runs when the button is pressed, creating and scheduling a fresh elevator command. That movement command owns the elevator until arrival or interruption. A second press creates another movement command, which interrupts the previous one and runs its cleanup before starting the new destination. No trips are queued. Do not add the elevator as a requirement of the outer runOnce: the movement command owns that requirement. The elevator factories stay unchanged and remain usable in sequences that wait for arrival. Canceling the short outer command after dispatch does not cancel the movement; cancellation and cleanup belong to the scheduled movement command. CommandScheduler is already imported in this project. getInstance() gives us the scheduler; schedule(...) starts the new movement command. This project uses the 2027 alpha API, which does not provide command.schedule().

After — green marks the added code

        operator.a().onTrue(Commands.runOnce(() ->
            CommandScheduler.getInstance().schedule(elevator.decreaseLevelCommand())));
        operator.y().onTrue(Commands.runOnce(() ->
            CommandScheduler.getInstance().schedule(elevator.increaseLevelCommand())));

Try the same experiment again

  1. Save your changes and restart the simulator. Reconnect AdvantageScope if necessary and enable Teleoperated mode.
  2. From BOTTOM, tap Y to select MID. About one second later, tap Y again. SelectedLevel should now change to TOP before the elevator reaches MID.
  3. Wait for TOP. Tap A, wait about one second, and tap A again. Selection changes through MID to BOTTOM while traveling.
  4. Hold Y from BOTTOM: it advances only once, to MID. You still need a release and another press to request TOP.

MovementActive may stay true across replacement: cleanup and the new command can run within one robot loop. The changed selected height shows that the new trip was requested.

Screenshot placeholder: one short trace showing the second Y press changing the destination from MID to TOP before arrival.

Two different command lifetimes

The button command finishes after scheduling the movement. The elevator command finishes at arrival, or is interrupted by a replacement. For a sequence that must wait for the elevator, use goToLevelCommand directly; do not wrap it in this button-dispatch pattern. Interrupting the movement still runs its cleanup. Ending or canceling the outer button command does not end the movement it launched.
